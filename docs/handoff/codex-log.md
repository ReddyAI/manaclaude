### Open problems, highest priority first

1. **Worker entry fails runtime startup, blocking deployment after the test gate is fixed.** Files: `backend/src/index.ts:21`, `backend/wrangler.toml`, `backend/deploy/config.ts`, `.github/workflows/deploy-worker.yml`. The entry exports the string `SYNC_CRON`. Local workerd rejects it with `Incorrect type for map entry 'SYNC_CRON': the provided value is not of type 'function or ExportedHandler'`. The generated deploy configuration uses the same entry. Suggested fix: move the constant into a non-entry module or use a dedicated entry exporting only supported handlers; add an actual runtime startup/health smoke check. Local reproduction confirmed; a remote deployment was not attempted.

2. **Plaid disabled does not prevent syncing an existing Plaid connection.** Files: `backend/src/sync/run.ts` (`syncConnection`, `skipReason`, `syncDueConnections`), `backend/src/link/service.ts` (`plaidEnabled`). The flag is checked by linking, but manual sync and cron can still invoke the adapter when a saved connection exists. Reproduced with the flag off and an in-memory fetch counter. Suggested fix: enforce the disabled state before every sync/probe provider call, including forced sync and cron, and assert zero outbound attempts in tests. Keep the deployed switch off.

3. **Statement imports can ignore the selected destination and relabel amounts with another currency.** File: `backend/src/imports/service.ts` (`resolve`, `matchAccount`, `toTransaction`). A name/mask match is tried before the explicitly selected account. Selecting an INR account while a named QIF matches a different USD account routes the row to the USD account. Commit copies the numeric amount and sets its currency to the destination's currency without checking for a mismatch. The same resolution is shared by OFX and PDF. Suggested fix: honor an explicit destination for a single-account file; require explicit mapping for multi-account files; reject currency mismatches instead of silently changing the money's meaning. Wrong destination reproduced locally.

4. **Linking the same bank through different providers creates duplicate accounts.** File: `connectors/src/sync/accounts.ts` (`planAccountSync`). Matching uses provider `externalId`, so the same invented name/mask with a different provider ID creates another account and duplicates balances/history. Conversely, equal IDs from unrelated providers can be treated as a conflict because provider namespaces are not checked. A repair that obtains new provider account IDs has the same identity problem. Suggested fix: namespace provider IDs and add an explicit, user-confirmed mapping to an existing account when linking or repairing; preserve its transactions and selected provider. Do not silently merge by name alone. Duplicate creation reproduced locally.

5. **Selling the last holding can leave it in the investment portfolio.** Files: `backend/src/sync/apply.ts:194`, `connectors/src/sync/investments.ts`. Investment reconciliation is skipped when both holdings and activity arrays are empty. A successful snapshot of an empty portfolio therefore leaves old holdings behind. Suggested fix: represent snapshot completeness separately from an unavailable/partial response, then reconcile all covered investment accounts, including empty ones. Reproduced with a holding followed by an empty snapshot.

6. **A second device can overwrite backend settings with its own defaults.** Files: `apps/mobile/src/data/backend/sync.ts` (`refreshDataset`, `watchSettings`), `apps/mobile/src/data/settingsStore.ts`. Dataset settings are loaded into the finance store but never into the settings store. Changing one setting sends all server-backed settings from the local store; a fresh device can re-enable backend AI after it was disabled elsewhere, or overwrite money policies. Suggested fix: hydrate settings from the authenticated backend before enabling writes, and send only intentional changed fields with a defined conflict policy. Static trace; Claude-owned follow-up.

7. **A first ordinary CSV import cannot create its destination bank account.** Files: `apps/mobile/src/features/import/ImportScreen.tsx`, `packages/shared/src/import/csv.ts`, `backend/src/imports/service.ts` (`resolve`, `commitImport`). An ordinary Date/Description/Amount CSV has no account metadata. On an empty database, “From the file” yields `needs_account` rows but no `accountsToCreate`; pressing Import reports success with zero added and every row skipped. There is no manual non-cash bank-account creation step in this flow. Suggested fix: offer a new statement account with name, type and currency, require a resolved destination before commit, and report unresolved rows as an actionable error. Reproduced with one invented CSV row.

8. **New statement accounts can use the wrong currency/date convention, with no usable correction controls.** Files: `backend/src/imports/service.ts` (`parseFile`), `apps/mobile/src/features/import/ImportScreen.tsx`, `apps/mobile/src/features/import/importApi.ts`. Without an existing destination, currency defaults to USD and ambiguous dates to month-first. A named QIF containing `03/04/2026` consequently creates a USD account dated March 4, even when the intended statement is INR/day-first. CSV can warn “Change it”, but the UI only offers three column selectors when mapping is missing; it exposes no date-format, currency, debit/credit or preamble controls. Suggested fix: require currency/date confirmation for ambiguous new accounts and expose the backend's mapping options even after automatic mapping. QIF defaults reproduced locally; missing controls confirmed by inspection.

9. **An interrupted first sync can stop retrying until the next daily boundary.** Files: `backend/src/sync/apply.ts` (`markConnectionError`), `backend/src/sync/run.ts` (`syncDueConnections`). A failed attempt sets `lastSyncAt` to now and changes status to `error`; cron selects `syncing` or connections whose last attempt predates the daily boundary. The next five-minute run skips the unfinished first sync, contrary to the “finishes within a few minutes” setup guidance. Suggested fix: preserve incomplete-sync state and schedule bounded retries/backoff separately from successful daily freshness. Reproduced with a fake failed first request and the next cron invocation.

10. **Sophtron completion is not replay-safe.** Files: `backend/src/api/link.ts` (`sophtronStatus`), `apps/mobile/src/features/link/SophtronFlow.tsx` (`follow`, `Waiting`). The session moves to `done` before connection creation, and later polls return `done` without connection IDs. The UI requires those IDs and otherwise keeps waiting. A lost success response, overlapping polls or a failure during finalization can strand the flow. Suggested fix: persist and replay the completion result, make finalization recoverable, and serialize polling rather than overlap requests every three seconds. Static trace.

11. **SnapTrade Repair can report success after a cancelled or unsuccessful login.** Files: `backend/src/api/link.ts` (SnapTrade complete route), `apps/mobile/src/features/link/BrowserFlow.tsx`. The repair branch loads authorizations but does not check that the saved authorization is present and enabled before calling `markRepaired`. The phone flow also calls complete after a closed browser window. Suggested fix: distinguish cancellation and verify the exact saved authorization is repaired before changing status. A failed repair must retain an actionable error and the existing connection. Static trace.

12. **Kite's daily sync can miss later trades permanently.** Files: `backend/src/sync/run.ts` (`lastDailyBoundary`, `syncDueConnections`), `connectors/src/adapters/zerodha_kite/index.ts` (`syncKite`). Normal daily freshness starts at 06:30 UTC, noon IST, but Kite `/trades` returns only that day's fills. After a successful noon sync, later fills are not fetched automatically that day; the next day's endpoint cannot recover them, and the token also expires daily. Suggested fix: schedule a provider-specific after-market sync while the daily token is valid and offer historical statement reconciliation. Confirm the provider's current expiry/session rules when implementing. Static trace against the adapter's documented API contract.

13. **WazirX trade history and cost basis are incomplete.** File: `connectors/src/adapters/wazirx/index.ts` (`syncWazirx`). Trade requests are generated only for nonzero holdings and choose a single INR-or-USDT market per asset; fully sold assets and other traded pairs are omitted. Each market fetches only 1,000 rows without pagination. Past USDT trades are converted using today's rate, changing historical cost and gains. Suggested fix: discover all relevant traded markets, paginate history, and retain native trade currency with historical FX. Keep balances distinct from history completeness. Static trace; live service availability was not tested.

14. **Coinbase Advanced Trade activity has an unverified coverage gap.** File: `connectors/src/adapters/coinbase/index.ts` (`SKIP_TRANSACTION_TYPES`, `mapCoinbaseTransaction`, `syncCoinbase`). `trade` and `advanced_trade_fill` ledger rows are explicitly discarded, while the alternative history calls are the v2 buys/sells endpoints. There is no Advanced Trade fills request. If those fills are absent from the buys/sells responses, holdings can look current while purchase dates, lots and realized gains are missing. Suggested fix: verify this contract with sanitized fixtures for each supported account type, add the correct paginated fills source, and deduplicate by trade identity. The discarded types are confirmed in code; their presence in other provider responses needs verification.

15. **Changing or forgetting backend credentials can let an older request repopulate the screen.** Files: `apps/mobile/src/data/backend/sync.ts:106`, `apps/mobile/src/data/backend/datasetCache.ts`, `apps/mobile/src/features/settings/sections/BackendSection.tsx`. The singleton in-flight dataset promise is not keyed to URL/token and is not cancelled on configuration changes. Its response can overwrite sample data after “Forget token”, or replace data for a newly selected backend; the cache is also not scoped to that backend. Suggested fix: associate requests and cache with a configuration generation/identity, cancel or discard obsolete responses, and clear appropriately on forgetting credentials. Static trace; Claude-owned follow-up.

16. **Deployment can remain green when the deployed API is unreachable.** File: `.github/workflows/deploy-worker.yml` (health-check step). After all retries fail, the step prints a warning and exits successfully. The web job can proceed despite a broken backend. Suggested fix: fail after a bounded propagation window and check an authenticated API route as well as health, while keeping tokens out of logs. Static trace; workflow changes need separate authorization.

17. **Mobile recap tests depend on the real month and will break later.** File: `apps/mobile/src/features/recaps/__tests__/recaps.test.tsx:12`. Sample data follows today's date, but the month-switch test always clicks “October 2026”; after that month leaves the screen's rolling list, the test fails. Reproduced with the full mobile suite dated February 1, 2027: one failure, 135 passes. Other mobile tests also use `todayLocal()`/unseeded sample data, including budgets, recurring, planning, investments and transaction tests. Suggested fix: Claude should pass a shared fixed date to sample factories and the tested date-dependent code, using a fixed test clock where a screen reads the clock directly. Keep the intended assertions; do not replace them with the current month. No mobile edits were made under the current ownership restriction.

## 2026-11-12 — Statement safeguards and Monefy CSV import

Started from merged `main` at `9c1b00b`, on `codex/safe-statement-and-monefy-imports`. This implements the backend portion of the approved import work after PR #11. Findings **3 and 7** are guarded on the backend; **8** is only partially addressed because the correction controls belong to the mobile owner.

### Changes and files

- `backend/src/imports/service.ts`: an explicitly selected destination takes precedence over file name/mask matches. Multi-account files cannot be silently collapsed into one selected account; ambiguous name/mask matches require selection. Currency is captured at preview and checked again on save. Unresolved destinations, unacknowledged parse errors, ambiguous Monefy dates and empty periods produce errors instead of zero-row success. Currency-less QIF requires a selected account or explicit currency. Rejected destinations/currencies do not leave unlisted uploads in R2; a failed database record write removes its uploaded original.
- `backend/src/imports/monefy.ts`: recognizes the eight-column comma/decimal-point Monefy export, including its two identically named currency columns and UTF-8 BOM. Imports the original signed amount once; retains the converted amount, category text and description in notes. Supports quoted multiline descriptions and Unicode. Detects two-digit numeric dates without consulting today's date. Row identities preserve identical-row multiplicity and remain stable when export conversion rates change. English transfer labels are reported as unsupported, pending a verified transfer-export contract.
- `backend/src/imports/categories.ts`: preserves exact Monefy category labels, creating missing categories instead of fuzzy matching. Existing category treatment wins; a new label with negative rows is an expense category, otherwise income. Monefy categories/notes are marked as user edits. Import-time rules and automatic ATM/transfer inference are not applied to Monefy history.
- `backend/src/imports/safety.ts`: inclusive date-range validation, destination-currency checks, stored import-identity matching, and possible duplicate candidates. Amount/date similarity never silently skips a row. Candidates include same account, currency and signed amount within three days; descriptions are deliberately not proof of identity.
- `backend/src/imports/service.ts`: core account/category/transaction/split/mapping/completion writes now share one atomic D1 batch. Rechecks stored identities and duplicate candidates at commit, with a guard inside the batch for a concurrent sync. New account IDs are deterministic, preventing concurrent attempts from creating separate accounts for the same import name/currency. Failed batches roll back; abandoned commit leases can be reclaimed after five minutes using an injectable clock. Discard/undo cannot interrupt a saving import. Post-save transfer failures preserve committed status and return/store a warning.
- `backend/src/api/app.ts`: accepts the additive backend fields below. `backend/test/import-safety.test.ts` adds invented fixtures and regression tests; `backend/test/imports.test.ts` now asserts explicit review of a possible PDF/sync overlap instead of the previous amount-only automatic skip.

### Defaults and API handoff for Claude

No mobile, shared model, root config, workflow, dependency or lockfile edits. No provider calls, remote deployments, environment publication, flag changes or credential-encryption changes. Uploaded source material stays outside Git; no actual filenames, account labels, categories, descriptions, dates, amounts or source-file statistics are included here or in fixtures.

The API remains `format: 'csv'`; the backend adds optional fields without changing shared types:

| Request or response           | Field                      | Meaning                                                                                                                                                                                           |
| ----------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/imports` multipart  | `fromDate`, `toDate`       | Optional inclusive `YYYY-MM-DD` bounds. Neither means all parsed history. Invalid/reversed dates are rejected. These bounds do not change bank sync or cron.                                      |

Files still have the existing 20 MB upload cap; large previews can encounter D1 value limits and should use shorter periods.
- An import whose response is lost after commit remains visible as committed through `GET /v1/imports/:id`; a repeat commit returns the existing conflict response. Undo removes its transactions and retains the original file. Created accounts/categories remain, as before for accounts.

### Exact request contract for Claude

`POST /v1/accounts/manual`, `Authorization: Bearer <existing app token>`, JSON body. Entirely invented example:

```json
{
  "idempotencyKey": "b1309553-5329-4772-b642-cae13ecf551a",
  "name": "Orchard savings",
  "type": "savings",
  "currency": "INR",
  "subtype": "nre",
  "openingBalance": { "amount": 20000, "date": "2025-01-01" },
  "currentBalance": { "amount": 45000, "asOf": "2026-11-12T12:00:00.000Z" },
  "includeInNetWorth": true
}
```

- `idempotencyKey`: required, 1–200 ASCII letters/digits/underscores/hyphens; generate a UUID **once per creation intention and persist it with the original request until the outcome is known**. Retry the same request/key after timeout, a lost response, reload or double tap. Do not generate a fresh timestamp or key on each retry. Keys are scoped to this manual-creation API/database and do not expire. A new key creates a distinct account even if its name matches another account; this is not name-based account reconciliation.
- `name`: required, trimmed, 1–100 characters after trimming.
- `type`: required: `checking`, `savings`, `credit_card`, `brokerage`, `retirement`, `crypto`, `loan`, `mortgage`, `property`, `vehicle`, `other_asset` or `other_liability`. No default type and no linked connection are inferred. Cash keeps its existing route/contract.
- `currency`: required, exactly three uppercase letters, following the existing ISO-code convention. Both balance amounts use this account currency; no conversion or second currency field is accepted. The validator checks the code's shape, not an exhaustive ISO registry.
- `subtype`: optional, defaults to `null`; otherwise a trimmed 1–100-character label. Use applicable existing labels such as `nre`/`nro` for the chosen bank account, `demat` or `401k` where applicable. The shared model deliberately permits custom subtype strings, so the backend preserves the label without inferring or changing account type/currency from it. It does not impose a new exhaustive subtype taxonomy.
- `openingBalance`: optional or `null` (default). If provided, both `amount` and a real calendar `date` in `YYYY-MM-DD` are required. This records an explicitly supplied historical balance, not a transaction, a bank-history cutoff or proof of complete history. It sets `account.openedOn` to that date. Otherwise `openedOn` is `null`.
- `currentBalance`: **required**: either `null` for unknown or an object with both `amount` and `asOf`. `asOf` is a valid ISO UTC timestamp ending in `Z`, normalized to millisecond precision in responses. Omission is rejected. If both readings are supplied, opening date cannot be later than the UTC calendar date of the current reading. Readings need not be recent; callers must display their dates rather than claim freshness.
- All amounts are signed **safe integer minor units**, never floating-point major units. Asset balances mean what is held; liability balances mean what is owed as a positive number, with a negative value allowed for a credit. These are the existing `Account.balance` signs, not the transaction debit/credit sign rule. No sign inversion is performed.
- `includeInNetWorth`: optional; defaults to `true` only when a current balance was explicitly supplied, otherwise `false`. Explicit `true` with unknown current balance is rejected. Explicit `false` with a known balance is allowed.
- Unknown JSON keys at the top level or inside a balance object are rejected, including provider IDs and nested currency fields. No institution, mask, provider attachment, automatic sync or account-edit operation is part of this endpoint.

### Exact response, replay and read contracts

First creation: **201**, `{ "account": <AccountWithManualBalance>, "replayed": false }`. Matching retry: **200**, `{ "account": <current stored AccountWithManualBalance>, "replayed": true }`. Retry never resets the balance, name or other later account edits. The hash uses normalized values: trimmed names/subtypes, normalized timestamp, `null` defaults and effective net-worth setting. A successful retry does not insert snapshots again.

The `account` contains all existing `Account` fields, plus this optional additive property on accounts created by this route:

```ts
manualBalance?: {
  currentKnown: boolean;
  openingBalance: { amount: number; date: string } | null;
};
```

With a known current balance, `account.balance`/`balanceAsOf` hold the explicit amount/timestamp. With unknown current balance, the existing shared model still requires a number and timestamp, so these fields contain **compatibility placeholders**: `0` and the creation timestamp. **Claude must render unknown (not ₹0/$0 or a fresh balance) when `manualBalance.currentKnown === false`.** It remains excluded from net worth. Missing `manualBalance` means a legacy/provider/cash account, not proof of unknown or known provenance. This PR does not relabel older import-created accounts.

The same account shape is returned by `GET /v1/accounts` (`{ accounts: [...] }`) and in `GET /v1/dataset.accounts`. The creation key and request hash are never exposed by either read. Opening snapshots appear in the existing `balanceHistory`; neither opening nor current readings create transactions. Unknown current balance creates no current snapshot. There is no assumption that opening plus the imported rows reconciles to current.

Other new-account defaults: `institutionName`, `availableBalance`, `creditLimit`, `mask`, `connectionId`, `externalId` and `interestRate` are `null`; `hidden` and `isDefaultCash` are `false`; `createdAt`/`updatedAt` use the creation clock. Account IDs are server generated.

Errors keep the existing `{ error, message }` envelope: **400 `invalid_body`** for schema validation (malformed/missing JSON is 400 `bad_request`); **401 `unauthorized`** for missing/wrong authentication; **409 `idempotency_conflict`** when the key was used with different normalized details. A generic storage failure is **500 `internal`**; retain the original request/key for retry. The defensive **409 `account_missing`** result means the key exists but its account cannot be loaded; do not automatically create another. A 409 is not permission to silently rotate the key: reload/review the prior intention first.

A later poll resumes finalization without querying the already completed provider job. The final atomic D1 batch creates/repairs the connection, saves credentials when needed, increments a new connection's slot exactly once, stores `{ connectionIds, repaired }`, marks `done` and deletes the session secret. Any failed batch rolls all of those effects back. New connection IDs are stable for the session. No connection is exposed before its credentials exist. Existing account IDs, history, cursors and successful-sync timestamps survive repair.
- Subsequent completed polls replay the saved result exactly, including `repaired`, without provider requests or writes to the connection. They cannot reset a connection that has since synced or acquired another error. Immediate Sophtron refreshes without a returned job now also create a real replayable link ID (previously `linkId: ''`).
- `backend/migrations/0009_link_completion.sql` adds three nullable session columns (result and lease metadata) and an ephemeral `link_write_guard` table. `link/writes.ts` performs the constraint-guarded atomic writes. **Apply 0009 before this Worker.** Existing records are not rewritten. No production migration/deployment was performed. Rolling back to an older Worker loses these semantics; drain link attempts before a rollback instead of expecting the old Worker to understand `finalizing`.
- `backend/src/sync/credentials.ts` exposes `prepareCredentials` so the existing encrypted INSERT/UPDATE can join that atomic batch. `saveCredentials` still prepares and runs exactly that write. **`CREDENTIALS_SECRET` usage, HKDF inputs, AES-GCM, IV generation, encoding, merge/replace behavior and decryption are unchanged**; no key rotation, plaintext staging or alternative encryption is introduced.
- `backend/src/link/snaptrade.ts` verifies exactly the saved authorization with its saved SnapTrade user. Repair start refuses missing saved identity, opens the portal for that identity, and saves an encrypted session snapshot. Completion requires exactly one matching authorization with explicit `disabled: false`. Missing/disabled/unknown/duplicate matches refuse; provider HTTP, network and malformed-response failures also leave connection state untouched. A changed saved identity is rejected before completion, including changes while provider verification is in flight. Session completion and clearing the connection's repair error commit atomically. Overlapping completions cannot clear a newer error twice.
- `connectors/src/link/snaptrade.ts` fails closed on missing/nonboolean `disabled`; malformed list elements produce a controlled provider error. This also prevents new-link completion from accepting an authorization whose enabled state is unknown. No new provider endpoint is called.
- Session lifetime remains **30 minutes from creation**, including result replay and finalization retries; polling does not extend it. Expired attempts/results are unavailable and existing session creation cleanup removes them. Results do not expose provider identifiers or credentials. A **legacy `done` session without a saved result returns 409 `link_result_unavailable`** rather than claiming success without IDs or guessing which existing connection belongs to it. Such historical results cannot be reliably reconstructed; inspect Accounts before a deliberate new attempt. This compatibility limit does not apply to sessions completed by this implementation.
